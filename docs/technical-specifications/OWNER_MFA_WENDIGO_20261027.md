# Психотека: «Вендиго» – дополнительная защита Владельца

Релиз: 27.10.2026.

## Цель

Защита аккаунта Владельца двухфакторной аутентификацией TOTP после основного входа по email-коду. Строка «Вендиго» – только название функции, **не пароль**. Не помещать ее в сравнения секретов и не создавать статических секретных фраз в клиентском JS.

## Реализация

- `owner-mfa.html`, `owner-mfa.js`, `owner-mfa.css` – отдельная страница настройки и проверки MFA. Только для подтвержденного аккаунта с ролью `owner`.
- При отсутствии TOTP: `auth.mfa.enroll({factorType:"totp"})` выдает секретный SVG QR и запасной текстовый secret. Они отображаются только в браузере владельца, не попадают в GitHub/localStorage и не передаются в чат. Владелец сканирует, вводит 6-значный TOTP.
- `auth.mfa.challengeAndVerify({factorId,code})` включает проверку второго фактора. Возвращаемое `getAuthenticatorAssuranceLevel()` должно стать `aal2`.
- При наличии проверенного фактора, но новой сессии `aal1`, страница предлагает шестизначный код, и после подтверждения дает доступ к библиотеке и к управлению пользователями.
- Второй резервный фактор можно добавить на **другом устройстве** после первого входа с `aal2`; Supabase не выдает стандартные резервные recovery codes.
- В профиле Владельца отдельный пункт «Защита «Вендиго»». У участников и модераторов он скрыт.
- Главная `site-library-entry.js` предлагает подтвердить MFA для owner после email-OTP; при прямом открытии каталога `site-access.js` отказывает owner с `aal1` и направляет на `owner-mfa.html`.
- `manage-users.js` не показывает список при `aal1`, а предлагает перейти на страницу подтверждения MFA.
- `manage-user-roles` Supabase Edge Function, версия **2**: сервер делает `admin.auth.getUser(jwt)`, проверяет `owner` по таблице, а затем `admin.auth.mfa.getAuthenticatorAssuranceLevel(jwt)`. Без `aal2` отказ с `mfa_required` для списка и назначения/снятия ролей. Это защита на сервере, а не только невидимая кнопка.

## Включение владельцем

1. Установить отдельное приложение-аутентификатор (Google или Microsoft Authenticator), предпочтительно настроить резервное устройство.
2. Войти в Психотеку по почте, затем открыть `https://psyteka.onrender.com/owner-mfa.html`.
3. Нажать «Подключить защиту», отсканировать QR-код в приложении.
4. Ввести шесть цифр для подтверждения. После успешной проверки статус TOTP будет подтвержден `aal2`.
5. Добавить второй резервный фактор на ином устройстве и сохранить доступ к нему. Нельзя передавать скриншот QR, secret, SMS/OTP, код авторизации или backup в чат.
6. После перезахода использовать email OTP + код из приложения. При отсутствии устройства доступ к закрытым административным действиям будет невозможен до восстановления MFA через безопасный административный процесс.

## Проверки

- JS-файлы синтаксически проверены.
- Эмуляция enroll/verify и challenge/verify завершается `aal2`.
- При прямом открытии библиотеки owner `aal1` направляется на `owner-mfa.html`; owner `aal2` допускается.
- Серверная проверка `getAuthenticatorAssuranceLevel(jwt)` развернута через Supabase Edge Function; панель управления отображается только при `aal2`.
- **Живой вход с настоящим TOTP владельца еще не проверен**: QR и код доступны только владельцу. Никогда не выдумывать результат реальной активации.
- Публичные статические файлы по прямым URL по-прежнему не защищены backend, это отдельная задача для будущих платных тарифов.
